# امکان‌سنجی ارائه‌دهنده هوش مصنوعی برای رستوران‌های ایران
**تاریخ بررسی:** ۲۰۲۶-۱۱-۱۴. **وضعیت:** پیش از انتخاب و اتصال provider.  
**نتیجه راهبردی:** هیچ API پولی یا ارائه‌دهنده انحصاری نباید پیش‌شرط انجام سفارش دستی باشد. اتصال واقعی به ارائه‌دهنده باید بعد از تأیید منطقه جغرافیایی، مجوز تجاری، پرداخت و سیاست داده انجام شود.

## ۱. محدودیت مهم منطقه‌ای
بر اساس فهرست رسمی کشورهای پشتیبانی‌شده OpenAI API در تاریخ بررسی، ایران در فهرست نیست؛ OpenAI هشدار می‌دهد دسترسی یا ارائه دسترسی به خدمات API از مناطق خارج از فهرست می‌تواند موجب محدودیت حساب شود. بنابراین صرفاً مستقر بودن backend در Render فرانکفورت را نباید دلیلی برای مجازبودن ارائه آن سرویس به مشتریان ایران تلقی کرد. هیچ راهکار دورزدن محدودیت‌ها در این طراحی پیشنهاد نمی‌شود. باید پیش از انتخاب یک provider، شرایط جاری و مجوز استفاده برای بازار هدف با منبع رسمی یا پاسخ کتبی ارائه‌دهنده احراز شود.

منبع رسمی: https://help.openai.com/en/articles/5347006-openai-api-supported-countries-and-territories

## ۲. گزینه‌های فنی و تجاری
| گزینه | مزیت | ریسک/هزینه | تصمیم اولیه |
|---|---|---|---|
| API مدل زبانی سازگار با قرارداد chat و مجاز برای بازار هدف | کیفیت فارسی و ادغام سریع‌تر | هزینه به ازای درخواست، منطقه پشتیبانی، نگهداری متن، قطعی شبکه | بررسی و انتخاب بعد از راستی‌آزمایی شرایط |
| مدل متن‌باز/قابل میزبانی مستقل با مجوز مناسب | کنترل بیشتر روی داده و ارائه‌دهنده | GPU/CPU و نگهداری و کیفیت فارسی؛ Render Free مناسب inference سنگین نیست | گزینه فاز بعدی، نه وعده استقرار رایگان |
| استخراج‌گر قانون‌محور محدود به منو | بدون هزینه inference و نسبتاً قابل پیش‌بینی در متن صریح | درک ضعیف عبارت‌های طبیعی و قیاس‌ها، نباید AI نامیده شود | fallback شفاف برای مثال‌های ساده، در کنار ثبت دستی |
| ثبت دستی کامل | مستقل از provider، دقیق در موارد مبهم | زمان بیشتر برای پیشخدمت | مسیر اصلی قابل اتکا و همیشه فعال |

در یک دموی رایگان نباید سرویس شبیه‌سازی‌شده را «تحلیل مدل واقعی» معرفی کرد. می‌توان با mock در تست‌ها و محیط توسعه، گردش کار را اثبات کرد و برای نمایش عمومی غیرفعال‌بودن AI را صریح نشان داد.

## ۳. چک‌لیست ارزیابی تأمین‌کننده
۱. مستند رسمی درباره اجازه استفاده و ارائه خدمات برای کاربران مستقر در ایران؛ قوانین محلی و شرایط تجاری ارائه‌دهنده.  
۲. محل پردازش داده، خط‌مشی نگهداری و آموزش مدل، امکان حذف اطلاعات و قرارداد حریم خصوصی برای توضیحات سفارش.  
۳. کیفیت فارسی محاوره، اعداد فارسی/عربی، تطبیق با منوی محدود، جملات اصلاحی، یادداشت اختصاصی و عدم اختراع کالا.  
۴. پشتیبانی از JSON Schema strict یا fallback معتبر JSON و خروجی قابل کنترل؛ سقف توکن، timeout، error handling.  
۵. تأخیر p50/p95 در شرایط شبکه واقعی و ظرفیت هم‌زمان؛ سازگاری با Free plan Render و اختلال‌های محتمل.  
۶. قیمت واقعی با اندازه‌گیری prompt/menu، token output، نرخ ارز، محدودیت بودجه و امکان قطع مصرف.  
۷. امنیت کلید، host allowlist، ثبت trace بدون محتوا، SLA و مسیر قطع سرویس.  
۸. اگر صوت مطرح شد، پشتیبانی صریح فارسی گفتاری، مجوز ضبط/ارسال، هزینه جداگانه و تأیید متن قبل از پیشنهاد.  
۹. انتخاب قرارداد خروجی یکسان در backend برای تعویض provider بدون بازنویسی UI.  
۱۰. آزمون golden corpus و negative/security قبل از فعال‌سازی برای کاربر واقعی.

## ۴. بودجه و کنترل مصرف
برای هر درخواست، فقط آیتم‌های کاندیدای لازم و متن سفارش ارسال شوند، نه کل اطلاعات مالی یا تمام جدول‌های مشتری. quota و rate limit در سطح tenant/user و سقف هزینه روزانه داشته باشیم؛ در شرایط قطعی یا تمام‌شدن بودجه، ثبت دستی بدون شکست در دسترس باشد. اعداد قطعی بودجه و مدل تا وقتی pricing و دسترسی قانونی تأیید نشده‌اند تعیین نمی‌شوند. خطر مصرف کنترل‌نشده در OWASP LLM10:2025 توضیح داده شده است: https://genai.owasp.org/llmrisk/llm102025-unbounded-consumption/

## ۵. نتیجه برای پیاده‌سازی
- **انجام شود:** طراحی مستقل از provider، قرارداد پیشنهاد و validation، ابزار mock، UX اصلاح، تست و رفتار قطع سرویس.
- **مشروط انجام شود:** اتصال API واقعی، پس از بررسی مجوز عرضه برای ایران و تأیید بودجه/شرایط داده.
- **انجام نشود:** پرداخت یا روشن‌کردن سرویس پولی بدون اجازه، استفاده از کلید شخصی در فرانت‌اند، وانمودکردن mock به AI واقعی، فرض‌کردن تغییر موقعیت سرور به معنی رفع محدودیت منطقه‌ای.

این یک ارزیابی اولیه فنی/تجاری است، نه نظر حقوقی یا تأیید یک ارائه‌دهنده خاص. تاریخ و لینک منبع باید هنگام تصمیم خرید دوباره بررسی شود.
