# انتشار رایگان نسخه دمو برای ارزیابی استخدامی

این راهنما برای **فقط یک نسخه نمایشی، با داده‌های ساختگی** است. سایت واقعی، دیتابیس واقعی و ورود کاربران واقعی کار می‌کنند، ولی پرداخت بانکی انجام نمی‌شود. هزینه هدف با استفاده از پلن‌های رایگان Render و Neon برابر صفر است؛ پیش از ساخت منابع، طرح انتخاب‌شده را بررسی کنید. سرویس رایگان Render در بیکاری متوقف می‌شود و درخواست نخست ممکن است کند باشد. دسترسی از شبکه‌های ایران باید جداگانه آزموده شود.

**وضعیت:** هنوز سرویس واقعی راه‌اندازی نشده، URL عمومی یا اعتبارنامه‌ای ساخته نشده است.

## ۱. ساخت دیتابیس رایگان Neon

1. در https://console.neon.tech یک حساب متصل کنید و یک پروژه **فقط برای دمو** ایجاد کنید. پلن Free را انتخاب کنید؛ PostgreSQL 16 یا بالاتر مناسب است. اطلاعات مشتری واقعی وارد نکنید.
2. رشته اتصال **مستقیم و بدون pooler** با کاربر مالک دیتابیس را از Neon بردارید. این رشته فقط برای migration/seed است و نباید به برنامه عمومی Render داده شود. اتصال باید TLS داشته باشد (برای مثال `?sslmode=require`).
3. دو رمز مجزا و تصادفی بسازید: یک رمز برای نقش محدود `restaurant_runtime` و یک رمز قوی حداقل ۱۶کاراکتری برای حساب‌های ورود دمو. این رمزها را در Git، issue، اسکرین‌شات و پیام‌های عمومی ننویسید.

## ۲. ساخت و اجرای یک‌باره دیتابیس از GitHub Actions

در GitHub مخزن، به Settings → Secrets and variables → Actions → New repository secret بروید و این سه Secret را بسازید:

| نام secret | مقدار |
| --- | --- |
| `NEON_ADMIN_DATABASE_URL` | رشته اتصال مستقیم مالک دیتابیس Neon |
| `DEMO_DB_APP_PASSWORD` | رمز جدید و جداگانه برای نقش `restaurant_runtime` |
| `DEMO_LOGIN_PASSWORD` | رمز جدید برای پنج حساب دموی سایت |

در تب Actions، گردش‌کار **Bootstrap free demo database (manual)** را با گزینه Run workflow اجرا کنید و فیلد `verify_url` را فعلاً خالی بگذارید. گردش‌کار ابتدا مجوزهای نقش محدود را می‌سازد، migration را اجرا می‌کند و داده‌های دمو را فقط اگر هیچ رستورانی وجود نداشته باشد ایجاد می‌کند. موفقیت مرحله نهایی را بررسی کنید.

**مهم:** اجرای مجدد seed رمز کاربران موجود را تغییر نمی‌دهد؛ تغییر `DEMO_LOGIN_PASSWORD` روی دیتابیسی که قبلاً seed شده است، رمز ورود فعلی را عوض نمی‌کند. همچنین تغییر `DEMO_DB_APP_PASSWORD` نیازمند به‌روزرسانی رشته اتصال برنامه در Render است. برای شروع تمیز، پروژه آزمایشی Neon را به‌صورت مجزا و از نو ایجاد کنید.

اگر دسترسی ویرایش Secrets ندارید، می‌توانید همین مراحل را در رایانه شخصی با Node.js 22، محیط دارای `ADMIN_DATABASE_URL`، `DB_APP_PASSWORD`، `DEMO_PASSWORD` و `SEED_DEMO=true` و دستورات `npm install`، `npm run migrate` و `npm run seed` اجرا کنید. رمزها را به خط فرمان دارای تاریخچه یا فایل commit‌شده منتقل نکنید.

## ۳. آماده‌سازی رشته اتصال محدود برای Render

در Neon همان host، port و database رشته اتصال مالک را حفظ کنید ولی **username** را `restaurant_runtime` و **password** را مقدار `DEMO_DB_APP_PASSWORD` قرار دهید. در صورت وجود کاراکتر ویژه در رمز، آن را در URL به‌درستی percent-encode کنید؛ `sslmode=require` را نگه دارید. برای runtime از همین کاربر محدود استفاده کنید، نه کاربر مالک دیتابیس.

قبل از ادامه، با این رشته اتصال محدود باید بتوان به دیتابیس وصل شد. اگر اتصال خطای مجوز می‌دهد، migration را در GitHub Actions بررسی کنید. هیچ‌گاه برای «رفع مشکل» `NEON_ADMIN_DATABASE_URL` را در Render به‌عنوان `DATABASE_URL` استفاده نکنید.

## ۴. ساخت سایت رایگان روی Render

1. حساب GitHub را به https://dashboard.render.com متصل کنید. از New → Blueprint، مخزن `afakhari/restaurant-father` را انتخاب کنید. Render فایل `render.yaml` را می‌خواند.
2. بررسی کنید سرویس `restaurant-father-demo` از نوع **Web Service**، با `plan: free` و `runtime: docker` است. هیچ دیتابیس پولی Render در این Blueprint تعریف نشده است.
3. در زمان درخواست مقدار `DATABASE_URL`، رشته اتصال **محدود** مرحله قبل را وارد کنید. هیچ رمز دیگری نباید به محیط اجرای وب‌سرویس داده شود.
4. از تنظیم خودکار `PUBLIC_ORIGIN` بر پایه `RENDER_EXTERNAL_URL` و `COOKIE_SECURE=true` استفاده می‌شود. پس از استقرار، دامنه واقعی `https://...onrender.com` را از صفحه سرویس Render بردارید. نام دامنه پیش از انتشار قابل حدس‌زدن نیست.
5. مسیر `/api/health` باید پاسخ ۲۰۰ و `{"ok":true}` بدهد. در خطاهای اتصال دیتابیس، URL محدود و لاگ‌های Render را بررسی کنید؛ رمز را هرگز در گزارش عمومی کپی نکنید.

**هزینه:** Render Web Service روی Free و Neon روی Free بمانند. قابلیت‌های پولی، افزایش منابع یا خرید دامنه را فعال نکنید.

## ۵. آزمون دمو با URL واقعی

پس از استقرار، در Actions همان workflow را با `verify_url` برابر با آدرس HTTPS اصلی Render (بدون مسیر اضافی) اجرا کنید. اسکریپت `scripts/verify-public-demo.mjs` این موارد را بدون نمایش رمز بررسی می‌کند: سلامت سرویس، ورود و خروج پنج نقش، کوکی Secure و جداسازی داده‌های دو رستوران در خروجی پنل‌ها.

از مرورگر موبایل و دسکتاپ هم دستی تست کنید: پیشخدمت سفارش دوم را به یک میز باز اضافه کند؛ آشپز سفارش را آماده کند؛ پیشخدمت تحویل را ثبت کند؛ صندوق‌دار مبلغ را بررسی و تسویه کند؛ سپس کاربر رستوران دوم فقط داده‌های همان رستوران را ببیند. سناریوی خطا و قطع اینترنت هم آزموده شود. این آزمون HTTP جای ویدئوی واقعی و مرور دستی UX را نمی‌گیرد.

## ۶. تحویل نهایی

در فرم تسک، لینک **واقعی و تست‌شده**، اطلاعات ورود اختصاصی دمو به‌صورت خصوصی، لینک GitHub و ویدئوی توضیح‌دار ۵ تا ۱۰ دقیقه‌ای خودتان را وارد کنید. بیش از نیمی از ویدئو را به چرایی انتخاب دامنه، معماری و محدودیت‌های MVP اختصاص دهید؛ فیلم خودکار CI جایگزین این ویدئو نیست.

**محدودیت مهم:** بدون ایجاد حساب‌های خارجی و واردکردن اسرار توسط صاحب حساب، هیچ ابزار داخل مخزن نمی‌تواند Neon، Render یا URL واقعی بسازد. این راهنما و فایل‌های استقرار، آماده‌سازی‌اند نه ادعای اجرای عمومی.
